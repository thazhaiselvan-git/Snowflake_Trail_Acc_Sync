1. Summary

We propose to rebuild the custom asset schema category table, which is today loaded by the Oracle npf_common_pkg.npf_asst_typ_mgr + RULE_EVALUATION logic, as:

  • One view WPA_CSTM_ASSET_SCHEMA_CATG_VW holding the complete Oracle logic, so the logic lives in one place.
  • One target table WPA_CSTM_ASSET_SCHEMA_CATG_TBL that consumers read.
  • One load procedure WPA_CSTM_ASSET_SCHEMA_CATG_LOAD_SP doing a delta MERGE + DELETE.
  • Two serverless tasks: a regular refresh every 3 minutes, and an immediate refresh when a user changes a rule table, detected through streams.

2. Background & problem

  • The target table holds, for each customer's custom schema, the super / sub category code and description of every asset the customer holds or has traded, using reporting type WLT.
  • In Oracle the procedure is called once per customer schema × instrument. Each call either:
    • applies the custom override row (NPF_CSTM_SCHEMA), producing -C/-S codes, or
    • evaluates the schema's rules (NPF_CSTM_RULE_MSTR / _COND) against the standard category and the country, falling back to the standard values.
  • The current Snowflake load (stored procedure plus streams) is row-by-row in spirit, hard to review, and earlier versions produced every instrument for every customer, for example 399,775 instruments for one customer who holds about 6,104.
  • Goals: an Oracle-exact result, a simple and reviewable design, each large source read once, near-real-time freshness, and immediate reflection of rule changes.

5. Business logic (view)

Grain: one row per SCHEMA_ID × CUST_SK × INSTR_ID × ISS_TYPE. That is every customer schema crossed with every (instrument, issue type) that customer ever held, on any date, or transacted, with reporting type WLT.

#CTEOracle equivalentWhat it does / why
1cust_scope—Customers that have a custom schema. Limits the scan of the huge position and transaction tables.
2cust_instrCaller loop(customer, instrument, issue type) from positions (any date) plus transactions, de-duplicated with UNION. The issue type comes from the position or transaction row, because one instrument can carry several issue types, each with its own category.
3asset_std6-arg npf_asst_typ_mgrStandard category per (instrument, issue type) via LEFT JOIN NPF_ASSET_CATG, with defaults 30/20 Other Assets/Miscellaneous only when there is no mapping row. Country via LEFT JOIN NPF_DECODE. The inner join to NPF_ASSET means the instrument must exist, as in Oracle.
4combo—Distinct (super description, sub description, country). Rules are evaluated once per combo, not per instrument, with an identical result.
5rule_evalRULE_EVALUATIONActive rules LEFT JOIN conditions (zero-condition rules match) CROSS JOIN combo. Every rule is tested on every combo, as Oracle does; there is no join key. Counts conditions and matches, and sets an OR flag.
6rule_pickdesc_1 / desc_2Keeps matching rules: an OR rule needs any condition true, an AND rule needs all. Keeps the first (MIN_BY) and, when there is more than one match, the last (MAX_BY) matching rule.
7cstm_rowv_rec_cnt + custom cursorActive custom row (END_DT IS NULL) per schema and instrument. QUALIFY on the latest START_DT is a safeguard (0 duplicates today).
8calls / out11-arg npf_asst_typ_mgrPath 1 (custom row exists): custom descriptions with -C/-S codes. Path 2: COALESCE(last rule, first rule, standard) with <sup>-S / <sup>-<sub>-S codes.

6. Load mechanism

A Snowflake task can have either a fixed schedule or a stream condition. The two requirements (every 3 minutes, and immediately on a rule change) are therefore met by two tasks calling one procedure, so the load logic exists only once.

Procedure steps: WPA_CSTM_ASSET_SCHEMA_CATG_LOAD_SP

StepActionWhy
0Consume both rule streams (an INSERT that reads them into a session temp table, WHERE 1 = 0), committed on its ownDone before the snapshot, so a rule change made during the load stays in the stream and triggers the next run. A scheduled run also clears the streams, so there is no redundant triggered run.
aStage the view once into a temp tableThe heavy logic runs once; MERGE and DELETE read the same snapshot.
bMERGE on SCHEMA_ID, CUST_SK, INSTR_ID, EQUAL_NULL(ISS_TYPE)Inserts new rows; updates only rows whose values changed (IS DISTINCT FROM). LOAD_TS = when that row last changed.
cDELETE … WHERE NOT EXISTS in the stageRemoves rows the view no longer returns (ended custom row, customer removed from a schema). MERGE has no "not matched by source" clause.
—b + c in one transaction; on error ROLLBACK + RAISEReaders never see a half-applied load; the task run shows FAILED with the error.

Tasks

-- regular
CREATE OR REPLACE TASK ..._CATG_TSK
  SCHEDULE = '3 MINUTES'
  USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE = 'SMALL'
  TARGET_COMPLETION_INTERVAL = '3 MINUTES'
  SUSPEND_TASK_AFTER_NUM_FAILURES = 3
AS CALL ..._CATG_LOAD_SP();

-- immediate on rule change (triggered, no schedule)
CREATE OR REPLACE TASK ..._CATG_RULE_TSK
  USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE = 'SMALL'
  SUSPEND_TASK_AFTER_NUM_FAILURES = 3
  WHEN SYSTEM$STREAM_HAS_DATA('..._RULE_MSTR_CATG_STRM')
    OR SYSTEM$STREAM_HAS_DATA('..._RULE_COND_CATG_STRM')
AS CALL ..._CATG_LOAD_SP();

7. Change & failure scenarios

Key principle: the streams are only a "something changed" trigger. The procedure never reads rule data from them; every run recomputes the full result from the base tables. So consuming a stream can never lose a change.
ScenarioWhat happensOutcome
User changes a rule while no load is runningThe stream gets data → the rule task firesApplied in about 1 minute
User changes a rule during a scheduled load (after step 0)The change is after the stream offset, so it stays in the stream → the rule task runs right afterApplied right after the current run; never missed
Rule changed before step 0 of a scheduled runConsumed by that run and included in its snapshotApplied in that run
Both tasks fire at the same timeEach stages its own snapshot; Snowflake makes the second MERGE wait for the firstConsistent; no partial rows
Load fails after step 0Rollback, so the table is unchanged; the stream is already consumedThe next 3-minute run recomputes and applies it (≤ 3 min delay)
Persistent error (e.g. a duplicate key from bad data)Each run fails; the task suspends after 3 failuresVisible in TASK_HISTORY; the table keeps its last good state
Position / transaction / asset changePicked up by the 3-minute task≤ 3 minutes
Liquibase redeploys the scriptsCREATE STREAM IF NOT EXISTS keeps the stream offsets; CREATE TABLE IF NOT EXISTS keeps the dataNo reset, no data loss

8. Oracle parity & validation

  • Oracle comparison: 25 hand-picked (schema, instrument) cases covering all 7 Oracle branches (custom paths CC/SC/CS/SS; rule paths R1/RN/standard) were run through the Oracle procedure in VS Code and compared with Snowflake. All matched.
  • Independent validation script (Validation - CSTM Asset Schema Catg DY.sql): re-implements the Oracle logic separately, evaluating rules per instrument rather than per combo, and compares every row and every column by scenario. It also checks duplicates, NULLs, code formats, customer consistency, and the comparison with the old table.
  • Data checks: 0 duplicate active custom rows, 0 zero-condition rules, 0 empty strings in the key columns.
  • Grain check: unique on SCHEMA_ID, CUST_SK, INSTR_ID, ISS_TYPE (query included in the script).

11. Next steps

  1. Agree on the approach and the decisions in §10.
  2. Deploy to UAT2 through Liquibase; run the first load (CALL ..._LOAD_SP()).
  3. Run the validation script against the table and the per-customer counts against Oracle.
  4. Test the rule-change path: edit a rule, confirm the rule task runs and the target table reflects the change.
